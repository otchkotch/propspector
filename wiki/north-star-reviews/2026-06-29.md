## North Star Gaps

### 1. Jurisdiction Sufficiency Has Started, But Is Not Complete

The app now runs a seed jurisdiction sufficiency check for Wilmington. When a parcel is in Wilmington, it switches into the Wilmington bot, stops short of county-code math, and explains the missing Wilmington-specific dependencies in structured terms.

**Required next behavior**: expand this from Wilmington into a reusable profile-gap engine that says which jurisdiction bot is needed, which chapters are unmapped, and which GIS/code dependencies must be learned.

### 2. Wilmington Revealed A Non-Bounded Zoning Distinction

`1021 Gilpin Avenue` resolves to parcel `2602130233`. Representative-point zoning returns `26R5C`, but full-parcel municipal zoning intersection sees both `26R3` and `26R5C`.

This is not merely "split zoning" in the simple sense. It is a non-bounded zoning distinction: a real regulatory signal that must be tested for materiality, area, buildable portion, and whether it is a map-boundary artifact.

**Required next behavior**: zoning-by-area materiality testing before applying a municipal district.

### 3. Code Interdependency Is Still Mostly Manual

The personal journal is clear: zoning cannot be treated as singularly superior. Current code logic still leans heavily on zoning/use/bulk tables and selected protected-resource rules. It does not yet map cross-chapter dependencies such as subdivision, streets, fire, utilities, stormwater, historic review, public works, fees, or discretionary approval.

**Required next behavior**: a code dependency map per jurisdiction profile.

### 4. Adjoining Parcels And Access Are Not Yet Computed

The architecture now names adjoining parcels, frontage, and access, but the app does not yet calculate them as a shared service. This is a major feasibility blind spot.

**Required next behavior**: adjoining parcel detection, ownership comparison, frontage classification, and access-to-street/highway/boulevard/alley/easement screening.

### 5. Entitlement Risk Is Not Yet A Data Layer

Neighborhood character and political power are now logged as required feasibility factors, but the app does not yet score or explain them. It should not pretend political risk is law, but it must identify when discretionary approval and neighborhood context can dominate the practical answer.

**Required next behavior**: separate code yield from entitlement risk.

### 6. Unexpected Capital Costs Are Missing

The journal specifically calls out utility connection fees, cut/fill costs, road construction, and similar hidden costs. Current value screens compare income potential but do not yet screen capital burden.

**Required next behavior**: add a capital-risk checklist and later cost ranges.

### 7. Review Runtime Needs Fast And Slow Lanes

The full review took long enough to expose a process smell. Some checks should return quickly: jurisdiction, parcel, address, zoning, profile sufficiency, and known calibration signals. Slow geometry/resource checks should be separable.

**Required next behavior**: split North Star review into quick jurisdiction review and deeper evidence review.

## Operating Thesis Update

The next evolution is not "more formulas." It is jurisdictional self-awareness.

PropSpector should first ask:

1. Do I know this jurisdiction?
2. Do I know the right code chapters?
3. Do I know the parcel's physical/access/neighborhood context?
4. Do I know which approvals are objective and which are discretionary?
5. If not, what bot/profile must be created?

Only then should it calculate yield.
